# 架构设计说明

## 1. 设计原则

- **领域优先**：围绕 `Model / Mesh / Material / BC / Load / Solver / Result` 建模，而不是围绕界面页面建模
- **内核与界面解耦**：GUI 不直接操作低层矩阵，统一经由应用服务层调用
- **Python 编排，C++ 求解**：Python 负责流程、配置、AI、可视化；C++ 负责单元计算、装配、求解热点
- **先 2D 静力学，后多物理扩展**：避免一开始把体系做得过泛化
- **结果可验证**：任何核心算法都必须能通过 patch test、解析解或标准算例验证

## 2. 推荐模块边界

### Python 层

- `fem.domain`: 节点、单元、材料、边界、载荷、模型
- `fem.services`: 模型校验、求解流程编排、结果转换
- `fem.adapters`: C++ 核心绑定适配层
- `ui`: GUI 视图、交互命令、模型树、渲染
- `ai`: 题目解析、建模建议、解释器

### C++ 层

- `mesh`: 节点/单元连接信息
- `material`: 线弹性材料矩阵
- `element`: T3/Q4/T6 单元
- `assembly`: 全局刚度与载荷组装
- `solver`: 稀疏线性求解器
- `post`: 应力应变恢复
- `bindings`: pybind11 暴露接口

## 3. 为什么不建议一开始就把 GUI 和求解深度耦合

如果界面按钮直接操纵节点、刚度矩阵和求解流程，后续会出现：

- 算法替换困难
- 自动化测试困难
- AI 自动建模难以复用相同流程
- 工程导入/导出能力难扩展

所以建议把“求解一个模型”抽象为稳定服务接口：

```python
result = solve_linear_static(model, solver_config)
```

GUI、CLI、AI 三者都走同一条路径。

## 4. 推荐演进路线

### Phase A

- 2D 线弹性静力学
- T3
- 稠密矩阵验证版

### Phase B

- Q4 / T6
- 稀疏装配
- Cholesky / LU

### Phase C

- GUI 建模与后处理
- 结果云图、变形图

### Phase D

- AI 题目解析
- 建模建议
- 结果解释

## 5. 关键技术决策建议

- C++ 数值库优先考虑 **Eigen**
- Python 侧数组接口统一使用 **NumPy**
- 可视化优先考虑 **PyVista + Qt**
- 单元测试优先于 GUI 功能扩展

## 6. 未来可扩展方向

- 平面应力 / 平面应变统一抽象
- 非结构网格导入
- 后续接触、非线性、动力学
- 批处理与参数扫描
- AI 驱动的“问题到模型”半自动流程
